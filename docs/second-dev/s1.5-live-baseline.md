### 为什么选择 Function Calling

锁定版本为 langchain-openai 1.3.5、openai 2.45.0。实际读取安装客户端签名，确认 `ChatOpenAI.with_structured_output` 默认为 json_schema，支持 function_calling；并实际验证 `extra_body={"thinking":{"type":"disabled"}}` 的请求绑定方式。

原生默认请求：Fast/Grader/Evaluator HTTP 400。只换 Function Calling、保留默认 Thinking：Fast/Grader 仍 HTTP 400（tool_choice/thinking）。JSON Mode 最小请求成功，但还需要显式 Schema 提示，不能仅换 method 就保证复杂 Judge 输出。

Function Calling + 请求局部 Thinking disabled：三个角色均通过 Pydantic 校验；补丁后再次**只调用正式 Registry 的默认 with_structured_output**，Fast/Grader/Evaluator 全部成功，分别约 882/481/361 ms。这是最小协议探测延迟，不是 RAG 延迟。参考 [DeepSeek 官方请求协议](https://api-docs.deepseek.com/api/create-chat-completion/)。

`MODEL_STRUCTURED_OUTPUT_POLICIES` 是 JSON 对象，例如：

```text
{"model_<真实32位十六进制ID>:<真实版本>":"deepseek_function_calling"}
```

不按模型名称、URL 子串或 HTTP 400 自动探测/降级。未选择的 Profile 原样使用 ChatOpenAI/json_schema；普通 invoke/stream 不绑定 extra_body，Thinking 原行为不变。SDK max_retries 仍为 0，现有 ProviderExecutor 仍独占重试、错误分类、deadline。

策略是不可热修改的部署设置，按精确 Profile 版本固定，Registry 使用启动时副本。**现有 Model Snapshot wire contract 没有协议字段**：本轮另存 policy fingerprint，不能声称 catalog hash 单独覆盖协议选择。部署映射应视为该 Profile 版本的不可变配置，变更策略须使用新 Profile 版本/新实验并同步 API/Worker；不能对仍在执行的旧 Job 热换配置。本轮没有扩展正式控制面 Contract 或迁移数据库。

## 4. 上传故障的真实原因与最终 12/12 索引

### Excel、Parent 合并和 Judge 的已观测问题

实际 Milvus 读回 4 个 XLSX 的 55 个 Leaf；只有每份首 Leaf 带原始表头，**51/55 无表头**；没有 sheet_name、物理 row_start/row_end、source_anchor，page=0。不是所有表格都失败：价格 NX-002/NX-005、库存 NX-003 正确给值和单位。

准确源码：
- DocumentLoader.load_document / _load_from_langchain_docs：原始 Excel loader 和有限 metadata、固定字符分块。
- Milvus Writer + RETRIEVAL_OUTPUT_FIELDS / _format_retrieval_hit：当前固定投影。

- pipeline.grade_documents_node / await_hitl_node / synthesis：证据路由、HITL、只合并 answerable/partial 子结果。

**Judge 局限已实际出现**：table_query_001/004 的澄清 prompt 包含从初始公告取得的真实旧版功率/日期；最终 docs 为空，Judge 将其判为无支撑/编造。它能证明“当前 Judge 输入没有支持”，不能证明“这些事实不在知识库”。unsupported_claim_rate=0.18 必须带此限制，不当作独立人工幻觉率。

## 8. S2 推荐架构（本轮只设计）

推荐 **A：Milvus Leaf Dynamic Metadata + 命中 Leaf 来源显式传递**。本轮真实问题是参数行表示弱、Leaf 缺表头/单位/物理来源、Parent 命中不能定位行。先解决这些问题，不立即为全量 Parent provenance 增加数据库迁移。

| 维度 | A：Milvus Dynamic Metadata | B：PostgreSQL ParentChunk provenance |
| --- | --- | --- |
| 数据一致性 | provenance 跟随真实 Leaf；需额外写入/读回校验，现有文本 hash 不足以验证 metadata | Parent 正文与 JSON 同事务；仍需跨库 Leaf→Parent 校验 |
| 查询性能 | 不新增 DB 查询，但须限制字段大小 | 已有 Parent 查询可附带 JSON，增加存储、反序列化、缓存负担 |
| Parent/Leaf 映射 | 合并保留实际命中 Leaf ID/来源集合；不能用 min/max 冒充连续命中行 | 可存 Parent 完整范围；仍须区分 Parent 全范围与实际命中 Leaf |
| 向后兼容 | 新字段可选；旧文档明确“无来源”，新 parser 使用新 Build | Alembic/ORM/Store/缓存同步，旧行空值语义 |
| Version 隔离 | 完整 Tenant+KB+Document+Version+index scope | 相同，不由 JSON 替代版本过滤 |
| 迁移成本 | dynamic 已启用；无需正式 Milvus Schema 迁移，新 Version 重建 | PostgreSQL 迁移及重建；Milvus 叶子链仍需改造 |
| 实现/维护 | parser、writer/reader、merge、校验，范围较小 | 更多数据所有者和迁移维护，Parent 权威审计更直接 |

A 不等于“PostgreSQL Parent 可以保存任意 metadata”。如果需要任意 Parent 直接读取完整来源、独立数据库 provenance 审计，应该选 B，正式增加 JSON 字段和 Alembic；不要借用 acl_tags。

具体后续任务：

1. `backend/indexing/document_loader.py:DocumentLoader.load_document/_load_from_langchain_docs`：受控 Excel 行表示、每块产品标识/表头/单位、Sheet 和物理行/source_anchor。保持 loader 正式入口；先用开发 Case 和辅助 Ground Truth 写测试。
2. `backend/indexing/milvus_writer.py` 写入路径及 `milvus_client.py:MilvusStore/RETRIEVAL_OUTPUT_FIELDS/_format_retrieval_hit`：保留并验证 provenance，限制大小，保持 scope/版本隔离。
3. `backend/rag/utils.py:_merge_to_parent_level`：保留 bounded 的 matched Leaf 来源列表，区分 Parent 展示范围与命中来源；不改变检索算法。
4. `backend/indexing/parent_chunk_store.py:ParentChunkStore._to_dict/upsert_documents`：A 下不假装可持久化新字段；B 才同步 ORM、Alembic、缓存和 Store 测试。
5. `backend/documents/publication.py:DocumentPublicationConfig.build_profile/DocumentPublication._run_once`：新 parser/build identity、provenance 校验设计，candidate Version、Manifest、CAS 发布与失败清理。不得原地改 READY Version。
6. `backend/rag/evidence.py:pack_evidence`、安全文档投影、`backend/schemas/rag.py:RetrievedChunk`：S3 贯通证据/引用，S2 不顺带改 wire contract。

开发集没有双产品比较 Case、独立售后政策冲突 Case；只有版本功率冲突和购买日期保修查询。不能声称这些未覆盖能力已测；也不能为补齐它们调用冻结集。先记录缺口，后续新增辅助开发样本需单独版本化，保留当前 dev_v1 可比基线。
